# Подключение и данные для следующего обучения

## Что входит в эту поставку

- Отдельный пакет `classifiers/minilm` с настоящими весами MiniLM v7.
- Публичное подключение провайдера через `EventRouter.configure` → `bind_router`.
- Неблокирующий холодный старт через `ClassifierRegistry.create_async`: старые
  синхронные фабрики сохраняются; MiniLM загружает модель в фоновом потоке.
- `ClassificationContext.current_plan`: снимок фактически принятого плана этого агента.
- Ограниченные исполнимые планы в Runtime и проверка всех их действий до принятия.
- Необязательный приватный сбор входов, ответов и дальнейшего выполнения.
- Тесты обычных/условных планов, переходов фазы, очистки действий и нейросетевой реакции.

Unity, игровой сервер и протокол игры не меняются. Runtime Core не импортирует
PyTorch. Основная README и настройки работающего сервера не переключаются.

## Порядок обработки

1. Игра доставляет агенту разрешённое событие/наблюдение; Runtime проверяет его.
2. Дедупликация и ограничения очереди работают до оценки.
3. Доверенные critical-переходы оцениваются установленным правилом немедленно.
   `observe_rule_assessment(context, event, assessment)` позволяет записать этот
   результат до политики Router. Ошибка наблюдателя считается отдельно и не
   отменяет применение обязательного правила.
4. Остальные события поступают в `MiniLMClassifier.classify`. До вычисления
   сохраняется снимок; проекция превращает его в `ClassifierInput`.
5. Модель возвращает оценку и бинарное решение. Ошибка/тайм-аут/неподдерживаемый
   вход возвращают решение правил; источник и причина фиксируются отдельно.
6. Router применяет обязательные ограничения, затем либо оставляет план,
   либо ставит запрос пересмотра. Уже выбранная условная реакция выполняется
   через Scheduler после безопасной остановки предыдущего действия.
7. Трасса показывает фактически принятый ответ Brain и результат действий.

Результат классификатора — рекомендация для Router, а не право отправлять команды.
`should_request_brain_review` не означает, что вызов LLM обязательно состоялся:
событие может объединиться с другим, агент может умереть или матч закончиться.
Поэтому качество классификации и количество вызовов Brain считаются отдельно.

## Что именно записывается

| Запись | Основные поля |
| --- | --- |
| `actor.local-classifier-input.v3` | `call_id`, `event_id`, `session_id`, `actor_id`, `match_id`, время, версия Runtime, маршрут, `input`, `label: null` |
| `input.context` | задача, текущее действие, `current_plan`, до 4 используемых типов собственного игрового состояния |
| `current_plan` | версия `actor.executable-plan.v1`, ID, состояние, индекс шага, текущая команда, остаток шагов, неиспользованные условия, fallback |
| `actor.local-classifier-output.v4` | тот же `call_id`/`event_id`, ответ до политики Router, источник, hash весов, точный `model_input`, hash текста, оценка, порог, длительность |
| `actor.classifier-trace.v1` | `phase`, собственные session/actor, время, `details` с событием Router, принятым решением, планом, действием или результатом команды |

В `output` точный `model_input` есть только когда проекция успешно построена.
Для critical-правил нейросеть не вызывается: оценки модели там нет.
Трассы Router соединяются по `event_id`, ответы Brain — по `trigger_event_ids`
и `objective_id`, шаги — по ID плана, отправленные команды и ответы — по `command_id`.
Это связь по реальным идентификаторам, а не восстановленный задним числом план.

Текущий Skill не равен полному плану. Если Brain вернул одиночный `skill`,
`current_plan` остаётся `null`; условия и следующие действия не выдумываются.
Обсуждение передаётся отдельной полученной репликой с каналом и признаком
`from_self`, а не полной историей чата.

`RuntimeSession.trace_sink` — локальный синхронный диагностический callback
`(phase, fields)`. Он не является публичной консолью или памятью агента.
MiniLM подключает его только при включённой записи и восстанавливает предыдущий
callback при закрытии. Сбой записи не меняет игровое решение; счётчики ошибок и
пропусков нужно проверять перед использованием captures как датасета.

## Как получить обучающий пример

1. Сопоставить `input` и `output` по `call_id`. Проверить отсутствие пропусков,
   корректную версию и полноту логирования. Считать переполнение/тайм-аут отдельно.
2. Взять `model_input`, а не весь JSON с результатами Router и будущими действиями.
   Для новой версии проекции заново проверить соответствие входа реальному Runtime.
3. Дать человеку вход без ответа модели. Указать метку 0/1, пояснение,
   автора и статус проверки. Спорный пример исключить или оставить на ревью.
4. Все игроки, события, копии сообщений и варианты одного матча объединяются
   одной `group`. До обучения зафиксировать независимые матчи проверки.
5. Сохранять как ложные срабатывания, так и пропуски важных событий. Ответы
   модели и правил полезны для поиска расхождений, но не служат истинной меткой.
6. После обучения проверить правила жизненного цикла, условия плана, чат,
   задержки, новые целые матчи; только затем явно переключать модель.

### Что пока требует дополнительных данных или разработки

- Человеческая разметка живых диалогов: нынешний отложенный набор почти не содержит
  положительных обычных событий. Один удачный пример не доказывает превосходства.
- Состояние уже запущенного решения Brain и очереди пересмотра: в текущий
  `ClassifierInput` оно не входит. Успешное завершение Skill само запускает
  обычный следующий ход; без этого контекста нельзя автоматически размечать его
  как «нужен ещё один вызов».
- Показатели целого матча: выполненные задания, сообщения, убийства, собрания,
  голоса, принятые решения, ошибки SDK, причины остановки и расход токенов.
  Игровой итог используется для оценки матча, не как скрытый признак входа.
- Очередь обсуждения и крайний срок голосования: обычная реплика не должна
  бесконечно отменять почти готовый ответ Brain. Это отдельная задача Runtime;
  её нельзя исправлять разметкой всех важных сообщений нулём.
- Чёткая политика перехода на правила для каждой новой игры, версионирование
  адаптера и независимые проверки переноса качества.

Приватные логи, роли других игроков из postgame, будущие действия и исход матча
не подмешиваются в признаки. Обезличивание имён не делает сырую переписку
автоматически пригодной для публичной публикации. В этом коммите только
синтетические примеры и агрегированные отчёты.
